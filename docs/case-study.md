## 02. 기획 의도

- **배경**
  - 문서에 적힌 것: 피하고 싶은 방향으로 "판촉물 같은 상업적 느낌: 할인 배너, 팝업, 구매를 재촉하는 연출"을 정했어요(01). 주요 방문자는 "건강은 챙기고 싶지만 성분을 꼼꼼히 볼 시간이 없는" 사람이에요.
 
  - 많은 식품 쇼핑몰은 상품과 할인을 먼저 보여 주지만, 바쁜 사람에게 필요한 것은 "언제, 어떻게 먹으면 좋은지"라는 생활 속 쓰임새였어요.

- **목표**
  - 문서에 적힌 것: 전달하고 싶은 인상은 "정직하고 믿을 수 있음 — 매주 받아 먹어도 안심되는 재료와 만드는 방식"과 "편집자의 감각이 느껴지는 에디토리얼한 분위기"(01)
  - 방문자가 상품을 고르기 전에 "내 하루에 맞는 루틴"을 먼저 보고, 그 루틴이 자연스럽게 정기배송으로 이어진다고 느끼게 하는 것

- **타깃 사용자 한 줄**: 

기본 정보
가명: 김서윤 
연령대: 30대 초반, 33세
직업: 판교 IT 회사 마케팅 팀 대리, 주 5일 출근 
주로 쓰는 기기: 회사·집의 데스크톱 브라우저 

상황

오전 8시에 집을 나서서 9시까지 출근해요. 아침은 거의 거르거나 편의점 음료로 때워요. 
오후 3시쯤이면 출출해져서 과자나 단 음료를 찾게 되고, 그때마다 조금 후회해요. 
건강을 챙겨야 한다는 생각은 있어요. 하지만 성분표를 비교하거나 영양 정보를 찾아볼 시간과 여유가 없어요. 

이 사이트를 사용하는 상황

점심시간이나 퇴근 전, 회사 데스크톱으로 "아침 대신 먹을 만한 것"을 찾다가 들어와요. 
루틴 만들기에서 출근 시간(오전 8시)과 생활 패턴(주 5일 출근)을 고르면 바로 결과가 나와요. 출근 전 CCA 주스, 점심과 함께 그린 블렌드, 오후 3시 사과링으로 이어지는 하루 루틴이에요. 
결과를 보고 '이 구성으로 정기배송 신청'을 눌러 매주 월요일에 받아요. 장 보러 갈 시간을 따로 내지 않아도 돼요.

불편함 (페인포인트)

무엇을, 언제 먹어야 할지 모른다: 건강식품은 많지만 대부분 상품과 성분만 보여 줘요. 내 출근 시간과 하루 일과에 맞춰 언제 먹으면 좋은지는 알려 주지 않아요. 
비교할 시간이 없다: 성분을 하나하나 비교해 고를 여유가 없어서 결국 아무것도 안 사거나 늘 먹던 것을 사요. 
판촉에 지쳤다: 쇼핑몰에 들어가면 할인 배너와 팝업이 먼저 뜨고 구매를 재촉해서, 믿고 고르기 어려워요. (문서: 피하고 싶은 방향 "할인 배너, 팝업, 구매를 재촉하는 연출")
꾸준히 챙기기 어렵다: 마음먹고 사도 떨어지면 다시 사는 걸 잊어요. 매주 알아서 오면 좋겠지만, 정기배송은 해지가 번거로울까 봐 망설여요. (초안 / 사이트의 "해지·변경은 조건 없이 언제든"이 이 부분에 답함)

- **배경과 목표의 연결**
  - 할인과 상품 나열 대신 "출근 시간 · 생활 패턴 → 언제 무엇을"이라는 순서로 보여 주면, 시간이 없는 사람도 고민을 줄이고 정기배송까지 이어질 수 있다고 봤어요. 그래서 사이트 목적을 "섭취 루틴 만들기로 언제 무엇을 먹을지 제안하고, 그 구성대로 정기배송 신청까지 이어지게 함"(PROJECT_CONTEXT 1번)으로 정했어요.
  - 판촉물 느낌을 피한다는 배경은 구조 결정에도 이어졌어요(02 '고른 대안과 이유').
    - 가입 혜택 안내: 홈 상품 섹션 아래 문장 한 줄 — "할인 배너·구매 재촉 연출을 피함"
    - 회원가입: 팝업이 아닌 가벼운 페이지 하나 — "'팝업 없이' 원칙과 맞음"
    - 루틴 없이도 정기배송 신청 가능 — "루틴을 만들지 않은 방문자도 핵심 행동인 정기배송 신청까지 갈 수 있음"

## 03. 핵심 가설

- **가설 설정 배경 한 줄**: 사이트의 가장 중요한 행동은 정기배송 신청이고, 그 앞에 체험 요소로 "섭취 루틴 만들기"를 둔다고 기획 문서에 정했어요(01, PROJECT_CONTEXT 1번).
- **IF**: 루틴 만들기 화면(P-03)에서 출근 시간 슬라이더와 생활 패턴 칩을 고르는 즉시 '언제 무엇을' 결과와 일주일 구성이 바뀌고, 그 구성 그대로 정기배송 신청으로 넘어가는 버튼(P03-B01)이 결과 바로 아래에 있으면
- **THEN**: 방문자는 결과를 본 뒤 P03-B01을 눌러 정기배송 신청 화면(P-04)으로 이동하고, 신청 양식을 채워 신청 완료(P04-S04)까지 간다.
- **검증 방향**: 07의 테스트 케이스 중 루틴 선택(TC-12) → 정기배송 화면 이동(TC-13) → 회원가입부터 신청 완료까지의 사용 흐름(TC-29)이 끝까지 통과하는지로 확인해요.

### ① 루틴 만들기 (P-03)

- **무엇을**: 출근 시간 슬라이더(06:00~10:00, 눈금 5개)와 생활 패턴 칩 4개(주 5일 출근 · 주로 재택 · 유연한 일정 · 등교·통학) 중 하나를 고르면, 바로 아래 결과 영역이 0.2초 페이드로 바뀌어요. 결과는 '시간 + 상품 사진 + 한 줄'로 된 목록과 오른쪽 '일주일 루틴 구성' 상자예요. 생활 패턴마다 상품 2~4개가 달라지고, 출근·등교는 고른 시간 30분 전에 첫 상품이 놓여요. 고른 값은 저장돼 새로고침해도 남아요.
- **왜**: 03 가설의 IF 그대로예요. 루틴 결과를 별도 페이지로 나누지 않고 선택 바로 아래에 보여 주기로 한 이유는 "흐름이 끊기지 않고, 선택을 바꾸면서 결과를 다시 볼 수 있음"이에요(02 '고른 대안과 이유', 03 하단 패널 A).

### ② 루틴 → 정기배송 연결 (P03-B01 → P-04)

- **왜**: 가설의 THEN("정기배송 신청 완료까지 간다")과 연결돼요. 기획 문서에는 루틴 결과를 "정기배송 신청 구성으로 그대로 넘김"으로 정했고(PROJECT_CONTEXT 3번, 02), 혜택은 "혜택을 핵심 행동인 정기배송 신청과 연결"하려고 루틴 구성 정기배송에 붙였어요(02 '고른 대안과 이유'). 안내는 팝업이 아니라 "루틴 구성으로 신청하면 배송비가 매회 무료예요." 한 줄이에요(01 혜택 안내 방식).
- **어떻게**: 같은 루틴 데이터로 정기배송 구성을 만들고, 화면 이동 시 탭 상태를 넘겨요. 금액은 배송비 규칙을 모은 계산 함수(src/lib/pricing.js), 첫 배송일은 '신청 다음 날부터 가장 가까운 고른 요일'로 계산(src/lib/delivery.js)해요.

  - (초안) AI에게 일을 맡길 때는 "무엇을 만들지"보다 "어떤 문서를 기준으로, 어디까지 하고 멈출지"를 먼저 정해 두는 것이 결과를 맞추는 데 더 중요했다.

## 09. 회고

- **잘된 것**
  - 루틴에서 정기배송까지 다시 고르는 단계 없이 이어진 것. 루틴 만들기에서 본 상품과 수량이 정기배송 단계까지 그대로 담겨요.
  - 루틴 결과가 고르는 즉시 바뀌게 만든 것.
- **잘못된 것**
  - 처음 기획의 루틴 혜택("루틴을 만든 가입자"에게 첫 회 무료 · 매회 무료 · 무료 단품 자동 동봉)과 실제 구현이 달라져, 나중에 혜택 구조와 문구를 다시 정리했다.
  - 화면 디자인과 흐름 위주로 기획하다 보니 입력 항목의 규칙을 처음에 정하지 않았다. 완성 후 점검해 보니 주문 동의 체크, 전화번호 형식 확인, 비밀번호 확인 칸, 필수 표시가 빠져 있어 뒤늦게 추가했다. 다음 프로젝트부터는 회원가입·주문처럼 입력이 있는 화면은 필수 항목, 형식 확인, 동의 체크를 체크리스트로 만들어 처음부터 확인해야겠다.
  
- **도전한 것**: 
  - 직접 만들기 어려운 3D 느낌의 움직임을, 이미 만들어진 컴포넌트를 조정하는 방식으로 해결했다. 브랜드 무드에 맞게 변경해 파일을 열어 보는 형식으로 첫 화면을 바꿔 본 시도.

- **다음에 개선할 것**
  - 루틴 혜택 조건을 더 분명하게 정하기.
  지금은 '루틴 구성' 탭으로 신청하면 누구나 배송비가 매회 무료예요. 그런데 비회원은 루틴을 만들 수 없어서 기본 구성을 그대로 받거나 수량을 줄여도 혜택을 받아요. 그래서 "루틴을 따르면 혜택"이라는 의도보다 넓게 적용돼요. 다음에는 혜택을 받는 최소 조건(루틴을 만든 사람만, 또는 최소 수량)을 정하기.

## 10. 가설 검증

- **처음과 끝을 연결하는 서사**: (초안) 바쁜 30대 직장인이 상품과 할인보다 "언제 무엇을 먹을지"를 먼저 보게 하자는 생각에서 출발했어요. 출근 시간과 생활 패턴을 고르면 결과가 바로 바뀌고, 그 구성 그대로 정기배송 신청까지 이어지는 화면을 만들었어요.
- **검증 근거**
  - 확인된 것: 루틴 선택(TC-12), 같은 구성으로 정기배송 화면 이동(TC-13), 회원가입부터 신청 완료까지의 사용 흐름(TC-29)이 모두 통과했어요. THEN의 "신청 완료까지 간다"가 **화면 위에서 끊김 없이 가능하다**는 것은 확인했어요.
  - 한계: 누가, 몇 명이 테스트했는지는 ✏️ 직접 채우기. 테스트 케이스는 정해진 절차대로 따라 하는 확인이라, 타깃 사용자가 스스로 이 흐름을 끝까지 **선택하는지**는 아직 관찰하지 않았어요.
- **마무리 한 문장**: (초안) 루틴이 신청으로 이어지는 길은 만들었고, 사람들이 실제로 그 길을 걷는지는 다음에 확인할 차례예요.
